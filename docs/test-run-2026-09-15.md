## Diagnóstico del error “No autorizado”

La sesión de Store A se solicitó por HTTP cuatro veces, cambiando una sola condición cada vez. Luego se repitió la solicitud con `Referer` para ambas sesiones:

| Solicitud | Resultado |
| --- | --- |
| Sin cabeceras de origen (enlace abierto desde el chat) | HTTP 200 con página `No autorizado` |
| Solo `Origin: https://registered.example` | HTTP 200 con página `No autorizado` |
| Solo `Referer: https://registered.example/` | HTTP 200 con formulario de pago |
| `Referer` y `Origin` | HTTP 200 con formulario de pago |

La causa queda aislada: PayPhone valida el encabezado HTTP `Referer` de la navegación al formulario. `Origin` por sí solo no basta. Los enlaces entregados en el chat no llevan el referente del dominio registrado, por eso el navegador muestra “No autorizado”. Esto no indica que el token o los `storeId` sean inválidos.

Con `Referer` correcto, Store A y Store B devolvieron HTTP 200 y el formulario de pago.

Para continuar, el enlace debe ser un `<a>` dentro de una página servida por el origen WEB registrado y debe hacerse clic allí. No sirve pegar el enlace en la barra de direcciones. Como no se modificó ni desplegó el sitio del proyecto durante esta prueba, falta disponer de una página temporal de lanzamiento en ese dominio.

No se publican enlaces ni IDs de esas sesiones, porque son efímeros. Para repetir la prueba hay que generar sesiones nuevas y abrir sus enlaces desde el origen WEB registrado.

Las sesiones preparadas tienen vigencia limitada. Si caducan, se deben generar nuevas y no reutilizar sus IDs.
